Why n·G = O must hold

The points of secp256k1 form a finite group under addition, and G generates a cyclic subgroup of it. Adding G to itself repeatedly cannot produce new points forever, so the sequence G, 2G, 3G, … must return to the identity O. The smallest positive n with n·G = O is the order of G. For secp256k1 the whole curve has prime order n, so every point other than O has exactly this order.

The consequence is that scalars only matter modulo n: (k + n)·G = k·G + n·G = k·G. Private keys, nonces and signatures therefore live in Zn, and every scalar computation in ECDSA is reduced mod n. The second check says the same thing from the other side: (n−1)·G is the inverse of G, so adding G gives O.

My scalar_mul does not reduce the scalar first, so scalar_mul(n, G) really runs the full Double-and-Add over the 256 bits of n and lands on O only because addition, doubling and the modular inverse are all correct. That makes the check a real test of the arithmetic.

What would break if the implemented order were wrong by one

Suppose I had implemented n′ = n ± 1 in place of n. Then n′·G = ±G, not O, and reduction mod n′ no longer matches what the curve does. Everything that reduces mod the order uses the wrong modulus:

  • the nonce inverse k⁻¹ is computed mod n′ (and n′ = n + 1 is even, so it is not even prime: Fermat's inverse stops being an inverse);
  • s = k⁻¹(z + r·d) and the verifier's u₁ = z·s⁻¹, u₂ = r·s⁻¹ are reduced mod n′, so u₁·G + u₂·Q no longer equals k·G and valid signatures stop verifying;
  • the range checks on keys, nonces, r and s accept or reject the wrong values: with n + 1 the scalar n passes as a "valid" private key although its public key is the point at infinity;
  • low-s normalisation n′ − s gives a value that is not the negation of s, so the flipped signature is invalid, and BIP-32 child keys (IL + kpar) mod n′ no longer match the public derivation IL·G + Kpar.

Constant-time variant

scalar_mul_ladder is a Montgomery ladder: it always runs 256 iterations and each performs exactly one addition and one doubling, whatever the bit. I checked that it agrees with Double-and-Add on 20 random scalars in the demo and on 30+ scalars in my tests (including 1, n−1, n and 2256−1). Its limits are discussed in section 5.

The attack

Both signatures use the same k, so both have the same R = k·G and the same r. Subtracting the two signing equations removes the unknown d:

s₁ − s₂ = k⁻¹(z₁ − z₂)  ⟹  k = (z₁ − z₂) / (s₁ − s₂),    d = (s₁·k − z₁) / r   (mod n)

The attacker needs only the two signatures and the two message hashes, and the reuse is visible to anyone because the r values are equal.

Low-s. Real signatures are normalised, so either s may have been replaced by n − s, which is the signature made with −k. Flipping both only negates k and leaves d unchanged, so two cases remain: the signs agree (denominator s₁ − s₂) or differ (s₁ + s₂). My function computes d for both and returns the candidate whose public key d·G verifies both signatures. It returns the exact key in all four combinations, as shown above and asserted in test_extra.py.

Why RFC 6979 removes the vulnerability without making k predictable

RFC 6979 derives the nonce as k = HMAC-DRBG(d, z): a deterministic function of the private key and the message hash.

  • k never repeats across messages. A different message gives a different z and therefore a different k, so two different messages never share r under one key. Signing the same message twice gives the same signature, which reveals nothing new. The attack needs two different messages with one k, and that can no longer happen.
  • k is still secret. The private key d is the HMAC key. Someone who does not know d cannot compute k, and cannot distinguish it from a random value. Determinism only removes the dependence on a random number generator, which is what failed in the PlayStation 3 case (a fixed nonce) and in the 2013 Android wallets (a broken SecureRandom). It does not make k public.

My implementation reproduces the widely published vector for key 1 and message "Satoshi Nakamoto" (k = 0x8f8a276c…74f15d15), so the derivation agrees with other implementations.

The passphrase demonstration

In BIP-39 the mnemonic is the PBKDF2 password and the passphrase is appended to the salt ("mnemonic" + passphrase). There is no stored value to compare a passphrase against, so there is no wrong passphrase: each one produces a valid 512-bit seed and a valid wallet. 'correct horse' and 'correct horse ' differ by one trailing space and give unrelated addresses. This allows plausible-deniability wallets, and it also means a mistyped passphrase shows an empty wallet with no error.

The parent-key recovery attack

For a non-hardened child with index i, BIP-32 computes

I = HMAC-SHA512(cpar, serP(Kpar) ‖ i),    kchild = (IL + kpar) mod n  ⟹  kpar = (kchild − IL) mod n

The chain code cpar and the public key Kpar are exactly the contents of the xpub, so anyone holding the xpub can compute IL. One leaked child private key then gives the parent private key by a single subtraction. In the demo I gave the function only the neutered node of m/44'/60'/0'/0 and the private key of child 0; it returned 0xa29ac2cb…239b145a, the real parent key, and with it I derived the private key of sibling 1. The whole branch is lost, not one address.

Why the same attack fails against a hardened child

For a hardened child (index ≥ 231) the HMAC input changes to

I = HMAC-SHA512(cpar, 0x00 ‖ ser256(kpar) ‖ i)

IL now depends on the parent private key. To undo kchild = IL + kpar the attacker would first have to compute IL, which requires kpar, the value being sought. The xpub contains nothing that helps. My function refuses a hardened index with a ValueError, and my tests assert that. A further test shows that the non-hardened formula applied to a hardened child gives a wrong key. For the same reason an xpub cannot derive hardened children at all, which the last line of the watch-only block shows.

This is why BIP-44 hardens purpose', coin_type' and account': a leak below an account cannot climb above it.

The real deployment scenario

A merchant, payment processor or exchange puts an account xpub on a web server so that it can generate a fresh deposit address per customer without holding spending keys. Separately, one child private key leaks, for example from a hot wallet that signs withdrawals, a compromised device, or a key exported into another application. The two pieces together give the account's private key and every address under it, including all future ones. The xpub is meant to be safe to publish, so its exposure is not treated as an incident; that is what makes the combination dangerous.

What the table says

Shor's algorithm does not weaken ECDSA and Schnorr; it solves the discrete logarithm, so both fail completely. Replacements exist and are standardised, so the obstacle is size. A transaction grows by a factor of 8 to 37, and on a fixed block size throughput falls in the same proportion, from 7.75 tps to between 1.00 and 0.21. FN-DSA is the smallest but needs floating-point Gaussian sampling, which is hard to implement safely; SLH-DSA rests only on hash functions but has the largest signatures; ML-DSA is the middle option.

An asset that must stay secure for fifteen years: decide now or later?

Now. My argument does not depend on when a quantum computer will exist.

A blockchain is public and permanent. Every public key that is on chain today (P2PK outputs, reused addresses, every Ethereum account that has transacted) can be copied today and kept. This is harvest now, decrypt later: the attacker does not need the machine at the time of collection, only at some point while the asset is still worth taking. For signatures the "decryption" is computing the private key from the stored public key and spending the coins.

So I look at two durations that we do know. The asset must stay secure for X = 15 years. Migration takes Y years: choosing a scheme, changing consensus rules, upgrading wallets and hardware, and getting every holder to move coins to new outputs, which on a decentralised chain is slow and never complete. If a capable machine appears after Z years, the asset is safe only if X + Y < Z. We do not know Z, but with X = 15 and Y of several years, the condition already requires that no such machine exists for about two decades. Betting an asset on that is a decision in itself. And exposure cannot be undone later: a key that is public today stays public.

The costs in the table make waiting more dangerous, not less: because post-quantum signatures cut throughput by an order of magnitude, the migration cannot be rushed through in a few blocks when a threat becomes concrete. In the meantime the cheap measure is to keep keys behind hashes: never reuse an address, and move long-term holdings to outputs whose public key has never been published.

5. Implementation risk

A signature that verifies proves only that (r, s) is consistent with the public key. It says nothing about how k and d were handled on the way. Three ways the key can leak while every signature still verifies:

1. Timing and power side channels. In Double-and-Add the point addition runs only for the 1-bits of the scalar, so run time grows with the Hamming weight of k and a power trace shows the bits directly. Knowing k for one signature gives d = (s·k − z)/r, and even a few leaked bits per signature are enough (see 2). Mitigation: constant-time field arithmetic, a ladder with no secret-dependent branch or memory access, scalar blinding. My code has this problem. ecdsa._sign_with_nonce calls curve.scalar_mul(k, G), which branches on every bit of k, and computes k⁻¹ with inverse_mod (pow), whose time depends on its operand. scalar_mul_ladder equalises the sequence of point operations but still branches on the bit, and Python's big integers are variable-time, so it does not fix it either. HD derivation leaks the same way through private_to_public.

2. Bad nonces. A repeated k gives the same r, and d follows from two signatures (Part B). A k from a weak RNG can be guessed. A k that is merely biased, for example a few top bits always zero, repeats no r, yet a lattice attack on the Hidden Number Problem recovers d from a few hundred signatures. Mitigation: RFC 6979, and never a caller-supplied nonce. In my code ecdsa.sign accepts a nonce argument for the demonstration; any caller using it reintroduces the bug, so a real API would have to remove it.

3. Faults. If a bit flips during signing (voltage glitch, Rowhammer, bad hardware) the result is a faulty signature. With deterministic nonces, a correct and a faulty signature of the same message share k but differ elsewhere, and d can be solved from the pair. Mitigation: verify every signature before releasing it, and add fresh randomness to the nonce derivation. My sign returns the signature without verifying it first.

A fourth, mundane channel is d or k reaching logs, exception messages, swap or core dumps. My CLI prints the demo key on purpose, which is acceptable only because it is a published test key.
